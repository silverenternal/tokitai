## Overall architecture

```
+-------------------------------------------------------------+
|                     User-code layer                          |
|                                                              |
|   #[tool]                                                    |
|   impl MyTools {                                             |
|       pub fn my_method(&self, arg: String) -> String { }     |
|   }                                                          |
+-------------------------------------------------------------+
                              |
                              v
+-------------------------------------------------------------+
|                   Macro layer (tokitai-macros)               |
|                                                              |
|   1. Parse the impl block and its pub methods                 |
|   2. Extract method signatures and doc comments               |
|   3. Generate tool_definitions() (compile-time LazyLock init) |
|   4. Generate the call_tool dispatcher                       |
|   5. Generate per-method argument-parsing helpers            |
+-------------------------------------------------------------+
                              |
                              v
+-------------------------------------------------------------+
|                  Core types layer (tokitai-core)             |
|                                                              |
|   - ToolDefinition: tool definition                          |
|   - ToolProvider: provider trait                             |
|   - ToolError: error type                                    |
|   - ParamType: parameter type enum                           |
+-------------------------------------------------------------+
```

## Core components

### `tokitai-macros`

**Responsibility**: procedural macros, compile-time code generation.

**Input**:

```rust
#[tool]
impl Calculator {
    /// Add two numbers
    pub fn add(&self, a: i32, b: i32) -> i32 {
        a + b
    }
}
```

**Output**:

```rust
impl Calculator {
    // 1) tool_definitions() method (compile-time LazyLock init, current in v0.5.0)
    pub fn tool_definitions() -> &'static [ToolDefinition] {
        // generated by the macro
    }

    // 2) call_tool dispatcher
    pub fn call_tool(&self, name: &str, args: &Value) -> Result<Value, ToolError> {
        match name {
            "add" => self.__call_add(args),
            _ => Err(ToolError::not_found(name)),
        }
    }

    // 3) Per-method wrapper (generated). Parses the JSON args, runs
    // validation, then calls the user's method.
    fn __call_add(&self, args: &Value) -> Result<Value, ToolError> {
        // ...
    }
}
```

### `tokitai-core`

**Responsibility**: core type definitions, zero runtime dependencies.

**Types**:

| Type | Description |
|------|-------------|
| `ToolDefinition` | Tool definition; carries name, description, and input schema |
| `ToolProvider` | Provider trait |
| `ToolError` | Tool-call error |
| `ToolErrorKind` | Error kind enum |
| `ParamType` | Parameter type enum |

### `tokitai`

**Responsibility**: runtime library (optional); provides the full feature set.

**Features**:

- `default`: enable the full runtime
- `serde`: serde serialization support

## How the macros expand

### Parsing phase

1. **Parse the impl block**
   ```rust
   let impl_item: ItemImpl = syn::parse(item)?;
   ```

2. **Collect pub methods**
   ```rust
   for item in &impl_item.items {
       if let ImplItem::Fn(fn_item) = item {
           if is_public(fn_item) && !is_skipped(fn_item) {
               tools.push(extract_tool_info(fn_item));
           }
       }
   }
   ```

3. **Extract method information**
   - Method name
   - Parameter list (type and name)
   - Return type
   - Doc comments
   - Sync / async marker

### Code-generation phase

#### 1. Generate a `ToolDefinition`

```rust
fn generate_tool_def(tool: &ToolMethodInfo) -> TokenStream2 {
    let name = &tool.tool_name;
    let desc = &tool.description;
    let schema = generate_json_schema(&tool.params);

    quote! {
        ToolDefinition {
            name: #name,
            description: #desc,
            input_schema: #schema,
        }
    }
}
```

#### 2. Generate a JSON Schema

```rust
fn generate_json_schema(params: &[ParamInfo]) -> String {
    let mut schema = String::from("{\"type\":\"object\",\"properties\":{");

    for param in params {
        schema.push_str(&format!(
            "\"{}\":{{\"type\":\"{}\"}}",
            param.name,
            rust_type_to_json_type(&param.ty)
        ));
    }

    schema.push_str("},\"required\":[");

    for param in params.iter().filter(|p| !p.is_option) {
        schema.push_str(&format!("\"{}\",", param.name));
    }

    schema.push_str("]}");
    schema
}
```

#### 3. Generate the `call_tool` dispatcher

```rust
fn generate_call_tool(tools: &[ToolMethodInfo]) -> TokenStream2 {
    let match_arms = tools.iter().map(|tool| {
        let name = &tool.tool_name;
        let method_name = &tool.name;
        let param_parsing = generate_param_parsing(&tool.params);

        quote! {
            #name => {
                #param_parsing
                let result = self.#method_name(#(#param_names),*);
                Ok(json!(result))
            }
        }
    });

    quote! {
        match name {
            #(#match_arms)*
            _ => Err(ToolError::not_found(name)),
        }
    }
}
```

## Compile-time code generation

### Worked example: full expansion

**Input**:

```rust
use tokitai::tool;

pub struct Calculator;

#[tool]
impl Calculator {
    /// Add two numbers
    pub fn add(&self, a: i32, b: i32) -> i32 {
        a + b
    }
}
```

**Expanded code** (simplified):

```rust
pub struct Calculator;

impl Calculator {
    /// Tool-definition array (compile-time generated; in v0.5.0+ this is a method)
    pub fn tool_definitions() -> &'static [tokitai::ToolDefinition] {
        &[
            tokitai::ToolDefinition {
                name: "add",
                description: "Add two numbers",
                input_schema: "{\"type\":\"object\",\"properties\":{\"a\":{\"type\":\"integer\"},\"b\":{\"type\":\"integer\"}},\"required\":[\"a\",\"b\"]}",
            }
        ]
    }

    /// Tool-call dispatcher
    pub fn call_tool(
        &self,
        name: &str,
        args: &serde_json::Value,
    ) -> Result<serde_json::Value, tokitai::ToolError> {
        match name {
            "add" => {
                // Argument parsing
                let a: i32 = serde_json::from_value(
                    args.get("a").ok_or_else(|| {
                        tokitai::ToolError::validation_error("missing parameter 'a'")
                    })?.clone()
                ).map_err(|e| {
                    tokitai::ToolError::validation_error(
                        format!("parameter 'a' has the wrong type: {}", e)
                    )
                })?;

                let b: i32 = serde_json::from_value(
                    args.get("b").ok_or_else(|| {
                        tokitai::ToolError::validation_error("missing parameter 'b'")
                    })?.clone()
                ).map_err(|e| {
                    tokitai::ToolError::validation_error(
                        format!("parameter 'b' has the wrong type: {}", e)
                    )
                })?;

                // Call the original method
                let result = self.add(a, b);

                // Return as JSON
                Ok(serde_json::json!(result))
            }
            _ => Err(tokitai::ToolError::not_found(
                format!("unknown tool: {}", name)
            )),
        }
    }
}

impl tokitai::ToolProvider for Calculator {
    fn tool_definitions() -> &'static [tokitai::ToolDefinition] {
        // Returns the internal storage the #[tool] macro expanded
        Self::__get_tool_definitions()
    }
}
```

## Runtime call flow

### End-to-end call chain

```
User request: "compute 100 + 250"
       |
       v
+----------------------------------------+
| 1. The AI analyzes the request and     |
|    decides to call a tool.             |
|    -> {"name": "add",                  |
|        "arguments": {"a": 100,         |
|                      "b": 250}}        |
+----------------------------------------+
       |
       v
+----------------------------------------+
| 2. call_tool is invoked                |
|    calc.call_tool("add", args)         |
+----------------------------------------+
       |
       v
+----------------------------------------+
| 3. Dispatcher matches the tool name    |
|    match name { "add" => ... }         |
+----------------------------------------+
       |
       v
+----------------------------------------+
| 4. JSON arguments are parsed           |
|    a: i32 = 100                        |
|    b: i32 = 250                        |
+----------------------------------------+
       |
       v
+----------------------------------------+
| 5. The original Rust method runs       |
|    self.add(100, 250)                  |
|    -> returns 350                      |
+----------------------------------------+
       |
       v
+----------------------------------------+
| 6. The result is wrapped in JSON       |
|    json!(350) -> 350                   |
+----------------------------------------+
       |
       v
+----------------------------------------+
| 7. Returned to the caller              |
|    Ok(350)                             |
+----------------------------------------+
```

## Design decisions

### 1. Why generate code at compile time?

**Pros**:

- Type safety: the type checker catches type errors at compile time
- Zero runtime overhead: no reflection or dynamic type checking
- Better IDE support: completion and go-to-definition
- Automatic documentation: rustdoc can extract doc comments directly

**Cons**:

- Harder to debug macros: use `cargo expand` to see the expansion
- Slightly longer compile times

### 2. Why store the schema as `&'static str`?

- Generated at compile time, so the lifetime is `'static`
- Avoids runtime allocation and serialization cost
- Tool definitions never change during the program's lifetime

### 3. Why does `call_tool` return `Result<Value, ToolError>`?

- `Result`: the standard Rust error-handling idiom
- `Value`: lets you return any JSON-serializable value
- `ToolError`: provides structured error information

### 4. Why dispatch through `call_tool` instead of exposing methods directly?

- Uniform interface: the AI calls every tool in the same format
- Argument validation: parsing and validation are handled in one place
- Uniform error handling: one error type and message format

### 5. Why support async methods?

- Real-world operations are often async (database, network)
- tokio is the de-facto standard in the Rust async ecosystem
- The macro can generate the async dispatch code automatically

## Performance considerations

### Compile-time vs. runtime

| Operation | Compile-time | Runtime |
|-----------|--------------|---------|
| JSON schema generation | yes | no |
| Tool-definition registration | yes | no |
| Parameter type checking | partial | yes |
| Method dispatch | no | yes |

### Memory footprint

- `ToolDefinition`: ~100 bytes per tool (compile-time constant, no runtime cost)
- `call_tool` dispatcher: ~1 KB of code per tool
- Argument parsing: stack-allocated, no heap allocations

## Wrapper macros in v0.5.0

In addition to `#[tool]`, v0.5.0 ships a family of **wrapper macros** that decorate the generated `call_tool` dispatcher with cross-cutting behavior. They can be stacked and are emitted as additional `impl` blocks by the macros, so they compose cleanly with `#[tool]`.

| Macro | Purpose |
|-------|---------|
| `#[wrap]` | Generic wrapper hook for custom middleware (logging, metrics, transformation) |
| `#[openapi]` | Emit OpenAPI / Swagger documentation from the tool definitions |
| `#[delegate]` | Forward a subset of tools to a sub-provider (for composing services) |
| `#[retry]` | Retry failed calls with backoff |
| `#[rate_limit]` | Throttle calls per tool or globally |
| `#[circuit_breaker]` | Trip the circuit after repeated failures to protect the host |

These wrappers are designed to compose: you can apply several of them to the same impl block, and the macro pipeline resolves their order. They are the recommended way to add resilience and observability to a tool surface without hand-writing the dispatcher.
