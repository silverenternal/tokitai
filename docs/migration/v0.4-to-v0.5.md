# Upgrading from Tokitai 0.4 to 0.5

This guide walks you through upgrading an existing project from Tokitai
0.4.x to 0.5.0. It is meant to be read end-to-end during the upgrade
process.

## TL;DR

For most users: just bump the version. 0.5 is fully backward-compatible
at the source level. The new attributes and methods are purely
additive. The only breaking change is the
`tokitai_core::AsyncExecutor` trait signature, which was added in 0.4
and is rarely used directly.

- All existing `#[tool]`, `#[tool_type]`, `#[param_tool(...)]`, and
  `config!{ ... }` usage compiles unchanged.
- All existing `call_tool_sync` and `tool_definitions()` callers compile
  unchanged.
- One known macro bug ("duplicate `__call_X`" on mixed sync/async impls)
  is fixed — affected users may simply have to delete a workaround.
- One known `AsyncExecutor` design limitation
  (the `block_on_dyn` boundary requiring `Send + 'static`) is fixed:
  the new `block_on_dyn` + `unsafe` lifetime extension lets borrowed
  `&self` futures flow through the runtime-agnostic bridge.

## What's new in 0.5

- **7 new proc-macro attributes**: `#[wrap]`, `#[openapi]` + `#[openapi_op]`,
  `#[delegate]`, and the three resilience decorators `#[retry]`,
  `#[rate_limit]`, `#[circuit_breaker]`.
- **3 new `ToolDefinition` methods**: `to_openai_function()`,
  `to_anthropic_tool()`, and `to_mcp_tool()` — multi-schema export
  from a single `ToolDefinition`.
- **`tokitai_core::AsyncExecutor` is now object-safe** (its sole required
  method is `block_on_dyn`). The typed `block_on<F>(&self, F) -> F::Output`
  API has been re-introduced as the `AsyncExecutorExt` extension trait,
  which has a blanket impl for every `T: AsyncExecutor`.
- **2 `#[tool]` macro bug fixes** (see "Bug fixes that may surprise you"
  below).
- 50% speedup on the hot path of `call_tool` and `tool_definitions`
  (compile-time `#[inline]` work; no API change).

## Step-by-step upgrade

### Step 1: Bump the version in `Cargo.toml`

```toml
[dependencies]
tokitai = "0.5"        # was "0.4"
tokitai-core = "0.5"   # was "0.4"
tokitai-macros = "0.5" # was "0.4"
```

If you only depend on `tokitai` (the umbrella crate), the
`tokitai-core` and `tokitai-macros` re-exports follow automatically and
do not need to be listed separately.

### Step 2: Run `cargo build`

If you only used `#[tool]`, `#[tool_type]`, `#[param_tool(...)]`,
`config!{ ... }`, and the per-parameter attributes (`required`,
`default`, `example`, `validate`, `transform`, `min`, `max`,
`min_length`, `max_length`, `pattern`, `min_items`, `max_items`,
`multiple_of`), you should be done. 0.5 is fully backward-compatible
for these.

If you implemented `tokitai_core::AsyncExecutor` yourself, see
"AsyncExecutor migration" below. This is the only section with a
non-trivial code change.

### Step 3: (Optional) Try the new features

The new attributes are opt-in. Add them where they help; ignore them
where they don't. See "Trying out the new attributes" below for a
quick tour.

## Migration scenarios

### Scenario A: I only used `#[tool]`

**Action: nothing.** Your code compiles unchanged.

### Scenario B: I used `#[tool]` with mixed sync and async methods

**Action: nothing.** But you may have been hitting the
"duplicate `__call_X`" bug if your impl block had both sync and
async methods. Update to 0.5 and the bug is fixed automatically.

Before (0.4):
```rust,ignore
#[tool]
impl MyApi {
    pub fn sync_method(&self) -> i32 { 42 }
    pub async fn async_method(&self) -> i32 { 42 }
}
// ERROR in 0.4: duplicate definitions with name `__call_async_method`
```

After (0.5): compiles cleanly. The macro now emits a `__call_X_sync`
variant for the sync method and the `__call_X` for the async method,
and the dispatcher dispatches by signature.

### Scenario C: I implemented `tokitai_core::AsyncExecutor`

**Action: update your impl** to the new object-safe signature. The new
shape is shorter and is the only one the type-erased registry accepts.

Before (0.4, generic):
```rust,ignore
impl AsyncExecutor for MyExecutor {
    fn block_on<F: std::future::Future>(&self, fut: F) -> F::Output {
        // user code
    }
}
```

After (0.5, type-erased):
```rust,ignore
impl AsyncExecutor for MyExecutor {
    fn block_on_dyn(
        &self,
        fut: std::pin::Pin<Box<dyn std::future::Future<Output = ()> + Send>>,
    ) -> Box<dyn std::any::Any + Send> {
        // Drive the future to completion here. Most users do:
        futures::executor::block_on(fut);
        // Return a boxed unit; the typed output is recovered by the
        // `AsyncExecutorExt` blanket impl via a shared slot.
        Box::new(())
    }
}
```

If you want the natural typed API back, use the
`AsyncExecutorExt::block_on` extension trait. The blanket
`impl<T: AsyncExecutor + ?Sized> AsyncExecutorExt for T` gives every
`AsyncExecutor` a typed `block_on<F>(&self, F) -> F::Output` method
automatically — so callers that previously held a `&MyExecutor` and
called `.block_on(my_future)` still work, as long as the value is
behind a `&` or a `Box` (the extension trait is implemented for
`?Sized`, so trait objects also work).

The 0.4 generic signature is **not** retained; there is no migration
shim. Most users only ever see `block_on_async(...)` (the public
`tokitai_core` free function) which is unchanged.

### Scenario D: I want to use `#[wrap]`, `#[openapi]`, `#[delegate]`, `#[retry]`, `#[rate_limit]`, `#[circuit_breaker]`

**Action: opt in by adding the attribute.** The `tokitai` crate
re-exports all of them in 0.5. The full reference is
[`docs/wrap-architecture.md`](../wrap-architecture.md). Quickstart
examples:

`#[wrap]` — curated list of methods to expose, plus a generated
`new(client)` constructor:

```rust,ignore
use tokitai::wrap;

pub struct GitHubClient { client: reqwest::Client }

#[wrap(client = reqwest::Client, methods = [get_user, list_repos])]
impl GitHubClient {
    /// Look up a GitHub user by login.
    pub async fn get_user(&self, login: String) -> Result<User, String> {
        // user-written body that calls self.client.fetch(...)
    }
}
```

`#[openapi]` / `#[openapi_op]` — wrap a whole REST API from an
OpenAPI 3 spec at compile time:

```rust,ignore
use tokitai::{openapi, openapi_op};

#[openapi(spec = "openai_chat.json", base_url = "https://api.openai.com/v1")]
impl OpenAIClient {
    #[openapi_op(operation_id = "createChatCompletion")]
    pub async fn create_chat_completion(
        &self,
        body: ChatRequest,
    ) -> Result<ChatResponse, reqwest::Error> {
        // user code
    }
}
```

`#[delegate]` — write signatures, not bodies, when forwarding to an
inner client:

```rust,ignore
use tokitai::delegate;

pub struct OpenAIClient { inner: OpenAISdk }

impl OpenAIClient {
    #[delegate(to = "self.inner")]
    pub async fn chat(&self, req: ChatRequest) -> Result<ChatResponse, OpenAIError>;
}
```

`#[retry]`, `#[rate_limit]`, `#[circuit_breaker]` — resilience
decorators that wrap the body of a `Result`-returning function:

```rust,ignore
use tokitai::{retry, rate_limit, circuit_breaker};

#[retry(max = 3, backoff = "exponential")]
#[rate_limit(rps = 10, burst = 20)]
#[circuit_breaker(failure_threshold = 5, reset_timeout = "30s")]
async fn call_external(&self, endpoint: String) -> Result<String, String> {
    // body
}
```

These decorators can be stacked on a `#[tool]` method or on a plain
function. For async functions the inter-attempt sleeps are driven
through the registered `tokitai_core::AsyncExecutor` (if any), so they
do not block a runtime worker thread.

### Scenario E: I want to use the multi-schema export

**Action: call `to_openai_function()`, `to_anthropic_tool()`, or
`to_mcp_tool()` on any `ToolDefinition`.**

```rust
use tokitai::ToolProvider;

let tools = MyClient::tool_definitions();
let openai    = tools[0].to_openai_function();   // -> serde_json::Value
let anthropic = tools[0].to_anthropic_tool();    // -> serde_json::Value
let mcp       = tools[0].to_mcp_tool();          // -> serde_json::Value
```

The three methods share the same `input_schema` string, so any tool
discovered by `#[tool]` (or any of the new wrap attributes) is
serialisable into all three envelopes with no extra work. If the
stored `input_schema` is not valid JSON, each method emits `{}` in
its place so the surrounding envelope is always well-formed.

See
[`docs/wrap-architecture.md`](../wrap-architecture.md) section 4.7
for the full field-by-field table and the underlying protocol
references.

## Bug fixes that may surprise you

### Bug fix 1: `#[tool]` mixed sync/async methods

Before 0.5, an `impl` block annotated with `#[tool]` that mixed sync
and async methods produced *two* wrapper functions with the same
name (`__call_<method>`) — one for the sync path and one for the
async path — and the compiler rejected the program with "duplicate
definitions". The macro now picks the right wrapper name based on
whether the impl block contains any async methods:

- All-sync impl: each method gets a `__call_<name>` sync wrapper
  (unchanged).
- Mixed impl, sync method: gets `__call_<name>_sync` only (no async
  wrapper is emitted, so the name is unambiguous).
- Mixed impl, async method: gets both `__call_<name>` (async) and
  `__call_<name>_sync` (the sync-from-async bridge).

If you worked around the 0.4 bug by hand-splitting your impls, you can
collapse them back into a single `#[tool] impl` in 0.5.

### Bug fix 2: `#[tool]` sync-from-async with borrowed `&self`

Before 0.5, the macro's auto-generated `__call_<name>_sync` wrapper
for an `async fn` method constructed a future of the shape
`async move { self.method().await }`, which borrowed `&self` with the
wrapper's lifetime. The future was therefore not `'static`, but the
old `block_on_async` path required `F: 'static`. The result: any
`async fn` tool method that took `&self` could not be called through
the sync-from-async bridge. The `runtime_agnostic.rs` example in
0.4 documents this limitation explicitly and works around it by
making the tool methods sync and calling `block_on_async` from inside
the body.

In 0.5 the macro uses the type-erased
`tokitai_core::current_async_executor()` + `block_on_dyn(...)` path
and an `unsafe` lifetime extension to drive the non-`'static` future
to completion synchronously. The Tokio-runtime fallback path
(`Handle::block_on`, which is generic over the future's lifetime)
also works without any `'static` bound. If you have code that worked
around this bug, delete the workaround.

## Deprecations

None. 0.5 does not deprecate any 0.4 API.

## Removed

None. 0.5 does not remove any 0.4 API. The `TOOL_DEFINITIONS`
const-vs-method change (introduced in 0.4) and the `tool_attr` ->
method-level `#[tool(...)]` attribute syntax change (also 0.4) remain
the only API-shape breaking changes in the recent history.

## Trying out the new attributes

All seven new attributes are no-ops unless you add them. A safe
upgrade path is:

1. Bump the version, run `cargo build`, run your tests.
2. Pick one of the new attributes that maps to a real pain point in
   your codebase.
3. Migrate one call site.
4. Run the tests.
5. Repeat.

The new attributes do not interact with each other in surprising
ways: `#[wrap]` is the "curated method list" workflow on top of the
`#[tool]` codegen; `#[openapi]` is the "spec-driven" workflow; the
three resilience decorators are body-rewriting pre/post guards that
stack on top of any other attribute. See section 5 of
[`docs/wrap-architecture.md`](../wrap-architecture.md) for the full
composition table.

## Cross-language clients

The `examples/curl/`, `examples/py/`, `examples/go/`, and
`examples/js/` clients consume the same `ToolDefinition` JSON that
the new `to_openai_function` / `to_anthropic_tool` / `to_mcp_tool`
methods emit. They do not require a Tokitai recompile — the
HTTP+JSON wire format is unchanged from 0.4. The new methods are a
*purely additive* convenience for Rust callers that want the
provider-specific envelope inline.
